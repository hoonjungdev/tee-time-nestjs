# ADR 0001 — 모듈러 모놀리스 채택

- 상태: 채택
- 일자: 2026-09-02

## 배경

고객용 예약 서비스, 어드민 백오피스, 부킹 엔진을 하나의 서비스로 만든다.
"부킹 엔진"이라는 명명 때문에 서비스 분리가 자연스러워 보이지만, 이 프로젝트는
1인이 약 5주에 걸쳐 만드는 포트폴리오이며 운영 조직도 트래픽 요구도 없다.

동시에, 폴더만 나눈 단일 프로젝트는 경계가 지켜지지 않아 "모듈을 의식했다"는 주장을 뒷받침하지 못한다.

## 결정

**단일 프로세스 / 단일 데이터베이스의 모듈러 모놀리스**로 간다. 단, 경계는 실제로 강제한다.

1. 모듈마다 `*-contracts`와 구현 패키지를 **분리한다.** 구현 패키지는 `exports`로 진입점 하나만 연다.
   다른 모듈이 내부를 참조하려 하면 모듈 해석이 실패한다.
2. **모듈당 PostgreSQL 스키마 1개, DataSource 1개.** 스키마를 넘는 FK를 걸지 않는다.
3. **모듈 경계를 넘는 트랜잭션을 금지한다.** 경계 밖 일관성은 아웃박스 + 보상으로만 달성한다.
4. `dependency-cruiser`와 아키텍처 테스트를 CI에서 실행해 위반을 검출한다.
5. 모듈 내부 구조는 **복잡도에 비례해 다르게** 간다. Booking만 리치 도메인이고,
   Catalog/Identity/Notification은 Repository를 직접 쓰는 얇은 CRUD다.

## 대안과 기각 사유

### 마이크로서비스 분리

기각. 1인 포트폴리오에서 얻는 것이 없다.
서비스 간 통신·배포·관측 인프라를 갖추는 비용이 크고, 운영 경험을 보여줄 수단도 없다.
무엇보다 **예약 확정과 슬롯 점유를 하나의 트랜잭션으로 처리할 수 없게 되어**
이 프로젝트의 핵심 가치인 동시성 제어가 사가와 보상 로직에 파묻힌다.
분산 시스템 역량은 아웃박스 패턴으로 충분히 드러낼 수 있다.

### 계층형 단일 프로젝트 (Controllers / Services / Repositories)

기각. 만들기는 가장 쉽지만 경계를 강제할 수단이 없어, 규모가 커지면 모든 것이 모든 것을 참조한다.
어떤 판단도 드러나지 않는 구조다.

### 폴더로만 나눈 모듈러 모놀리스 (단일 패키지)

기각. 워크스페이스 패키지 11개가 과하다는 반론이 가능하지만, 패키지 분리는
모듈러 모놀리스를 "폴더만 나눈 모놀리스"와 구분하는 **유일한 실효적 장치**다.
ESLint 규칙은 규칙 파일을 고치면 뚫리지만, 선언하지 않은 패키지의 import는 해석되지 않는다.
문서로 지키는 규칙은 지켜지지 않는다.

## 결과

**얻는 것**
- 예약 확정·슬롯 점유·아웃박스 기록이 하나의 로컬 트랜잭션 안에 들어간다.
- 로컬 개발이 `docker compose up` + `pnpm dev` 두 줄로 끝난다.
- 경계 위반이 컴파일 또는 CI에서 즉시 드러난다.
- 장래 서비스 분리 시 모듈 단위가 그대로 후보가 된다.

**비용**
- 워크스페이스 패키지가 11개로 늘어 초기 설정이 번거롭다.
- 스키마 간 join이 불가능하다. 지역 기반 검색은 Catalog에서 `course_id` 목록을 받아
  Booking에 `IN` 조회하는 2단계가 된다. 의도된 비용으로 수용한다.
- 참조 무결성 일부를 애플리케이션이 책임진다 (마스터 데이터 소프트 삭제).

## 재검토 조건

아래 중 하나가 성립하면 특정 모듈의 분리를 검토한다.

- 특정 모듈만 독립적으로 스케일해야 할 정도의 트래픽 편중이 부하 테스트로 확인될 때
- 배포 주기가 모듈별로 명확히 달라질 때
- 외부 골프장 시스템 연동이 늘어 Catalog가 통합 계층으로 성격이 바뀔 때

**그 전까지 MSA 분리, Redis, 메시지 브로커 도입을 제안하지 않는다.**
근거 없이 도입된 인프라는 "왜 필요한가"에 답할 수 없어 감점 요인이 된다.
