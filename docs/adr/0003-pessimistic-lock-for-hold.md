# ADR 0003 — 슬롯 홀드에 비관적 락 사용

- 상태: 채택
- 일자: 2026-09-02
- 관련: ADR 0002

## 배경

이 프로젝트의 핵심 요구사항은 하나다.
**예약 오픈 시각에 다수 고객이 같은 슬롯을 동시에 요청해도 정확히 1건만 성공해야 한다.**

경합 대상은 슬롯 하나로 매우 좁고, 오픈 시각에 짧고 강한 스파이크가 발생하는 형태다.
즉 인기 슬롯에서는 **경합률이 사실상 100%**에 가깝다.

## 결정

**슬롯 row에 `SELECT ... FOR UPDATE`를 걸어 직렬화한다.** 이중 방어 구조를 취한다.

```sql
BEGIN;
-- ① 직렬화 지점
SELECT id, capacity, is_blocked, tee_at FROM booking.tee_slots
 WHERE id = @slotId FOR UPDATE;

-- ② 만료 홀드 정리 (락 안에서)
UPDATE booking.bookings SET status = 'Expired', updated_at = now()
 WHERE tee_slot_id = @slotId AND status = 'Held' AND hold_expires_at <= now();

-- ③ 활성 예약 확인 → 있으면 409
-- ④ INSERT
COMMIT;
```

- **1차 방어**: ①의 행 수준 배타 락
- **2차 방어**: `ux_bookings_active_slot` 부분 유니크 인덱스
  (`WHERE status IN ('Held','Confirmed')`). 애플리케이션 로직이 실패해도 오버부킹을 막는다.

두 방어 중 어느 쪽도 제거하지 않는다.

**이 경로는 raw SQL로 작성하고 유지한다.** 쿼리 빌더의 잠금 옵션은 조건에 따라 질의를
서브쿼리로 감싸 의도한 행에 락이 걸리지 않으므로 `queryRunner.query()`로 직접 쓰며,
"일관성"을 이유로 빌더로 바꾸지 않는다.

확정·취소 경로는 경합이 낮으므로 `xmin` 기반 낙관적 락을 쓴다. 경로별로 전략이 다른 것은 의도적이다.

## 부수 결정 — `Expired`를 별도 상태로 둔다

부분 유니크 인덱스를 "만료되지 않은 홀드"로 한정하고 싶었으나 불가능하다.

```sql
-- ❌ PostgreSQL의 부분 인덱스 술어는 IMMUTABLE 함수만 허용한다. now()는 STABLE이다.
WHERE status = 'Confirmed' OR (status = 'Held' AND hold_expires_at > now())
```

따라서 **만료는 읽기 판정이 아니라 쓰기여야 한다.**
홀드를 시도할 때 이미 잡고 있는 락 안에서 만료 건을 `Expired`로 전이시킨다(위 ②).

배경 스윕(`SlotExpirySweeper`)도 두지만, 역할은 **정합성 보장이 아니라**
오래된 `Held`가 목록 조회에 남지 않게 하는 위생 작업이다.

## 대안과 기각 사유

### 낙관적 락만 사용 (`version` 컬럼)

기각. ORM이 기본으로 제공하고 구현이 깔끔하지만, **경합률이 높은 경로에 맞지 않는다.**
인기 슬롯에서는 거의 모든 요청이 충돌해 재시도 폭풍이 발생하고,
사용자에게는 "다시 시도하세요"가 반복 노출된다.
낙관적 락은 충돌이 드물다는 가정 위에 서 있고, 이 경로는 그 가정이 거짓이다.

단, 경합이 낮은 확정·취소 경로에는 채택했다.

### Redis 분산 락 (Redlock 등)

기각. 현 단계에서 **도입 근거가 없다.**
단일 애플리케이션 + 단일 PostgreSQL 구성에서 DB 락으로 충분하며,
Redis를 추가하면 인프라 의존성과 락 만료·프로세스 사망 시의 안전성 문제가 새로 생긴다.
무엇보다 Redis 락은 DB 트랜잭션과 원자적이지 않아, 락은 획득했는데 INSERT가 실패하는 경우를
다시 처리해야 한다. `FOR UPDATE`는 트랜잭션과 생명주기가 같아 이 문제가 없다.

부하 테스트로 DB 락이 병목임이 증명되면 그때 도입하고, 그 과정을 문서로 남긴다.

### `SERIALIZABLE` 격리 수준

기각. 정확하지만 직렬화 실패 시 재시도를 애플리케이션이 전부 처리해야 하고,
경합 지점이 슬롯 하나로 명확한 상황에서 트랜잭션 전체에 비용을 지불할 이유가 없다.
행 락이 더 정밀하고 예측 가능하다.

### 유니크 제약만 두고 INSERT 실패를 잡기

기각(단독으로는). 실제로 오버부킹은 막히지만 `FOR UPDATE`가 없으면
②의 만료 홀드 정리를 안전하게 수행할 수 없고, 검증 로직(리드타임·차단 여부)이
경쟁 조건에 노출된다. 유니크 제약은 **2차 방어로만** 채택했다.

## 결과

**얻는 것**
- 오버부킹이 두 층에서 막힌다. 애플리케이션 버그가 데이터 사고로 이어지지 않는다.
- 만료 홀드 정리가 락 안에서 원자적으로 일어난다.
- 락 범위가 슬롯 1행이라 서로 다른 슬롯 간 경합이 없다.

**비용**
- 핵심 경로가 raw SQL이라 ORM 일관성이 깨진다. 의도적으로 수용한다.
- 락 대기가 길어지면 커넥션 풀이 압박받는다. 홀드 트랜잭션은 짧게 유지하며,
  **결제 호출을 트랜잭션 안에 넣지 않는다.** (홀드 커밋 → 결제 → 확정의 3단계)
- 동일 슬롯 요청은 직렬화되므로 처리량이 제한된다. 슬롯 단위이므로 전체 처리량 영향은 없다.

## 검증

M2 완료 기준에 포함한다. Testcontainers 기반 실제 PostgreSQL에서 검증한다.

- 동시 50 요청 → 정확히 1건 성공, 49건 409
- 홀드 만료 후 동일 슬롯 재예약 성공
- 결제 실패 시 슬롯 즉시 반환

## 재검토 조건

- 부하 테스트에서 슬롯 락 대기가 병목으로 확인될 때 → 분산 락 또는 큐 기반 직렬화 검토
- 조인 예약이 도입되어 슬롯이 부분 점유 가능해질 때 → 락 대상과 불변식 재설계 필요
