# ADR 0005 — 감사 로그를 대상 트랜잭션 밖에 둔다

- 상태: 채택
- 일자: 2026-09-02
- 관련: ADR 0001, ADR 0004

## 배경

어드민이 마스터 데이터와 예약을 바꾼다. 누가 언제 무엇을 바꿨는지 남아야 한다.

문제는 **바뀌는 대상이 여러 모듈에 흩어져 있다는 것**이다.

| 동작 | 소유 모듈 |
|---|---|
| 골프장·코스·운영 규칙·요금 규칙 CRUD | Catalog |
| 슬롯 생성, 예약 강제 취소 | Booking |

그리고 **모듈 경계를 넘는 트랜잭션이 금지**되어 있다(ADR 0001). 감사 로그를 어디에 두든,
Catalog의 변경과 감사 로그를 한 트랜잭션에 묶는 것은 규칙 위반이다 — 감사 로그가 Catalog
스키마에 있지 않은 한.

## 검토한 선택지

### A. 각 모듈이 자기 스키마에 감사 테이블을 둔다

`catalog.audit_logs`, `booking.audit_logs`.

- 장점: 대상 변경과 **같은 트랜잭션**이다. 유실이 없다.
- 단점: 테이블과 기록 코드가 모듈 수만큼 복제된다. "지난주에 누가 무엇을 바꿨나"를 한 번에
  볼 수 없고, 화면이 모듈별로 질의해 합쳐야 한다. 새 모듈이 생길 때마다 같은 것을 또 만든다.

### B. Identity가 소유하고, 각 어드민 핸들러가 `IAuditApi`를 호출한다

- 장점: 핸들러가 before/after를 정확히 안다. 무엇이 바뀌었는지 값 수준으로 기록할 수 있다.
- 단점: 어드민 핸들러 20개를 전부 고쳐야 하고, 새 어드민 기능마다 호출을 잊으면 조용히
  빠진다. **그리고 여전히 별도 트랜잭션이다** — 경계를 넘으므로 A의 장점을 얻지 못한다.
  값을 정확히 얻는 대가만 치르고 원자성은 못 얻는다.

### C. Identity가 소유하고, `/api/admin/*` 요청을 미들웨어가 기록한다

- 장점: 기록 지점이 **하나**다. 새 어드민 엔드포인트는 자동으로 남는다. 잊을 여지가 없다.
- 단점: before/after를 값 수준으로 알 수 없다. 요청 본문과 응답 상태만 남는다.
  그리고 별도 트랜잭션이므로 유실 가능성이 있다.

## 결정

**C를 택한다.** Identity가 `identity.audit_logs`를 소유하고, `/api/admin/*`에 붙는 미들웨어가
성공한 변경 요청을 기록한다.

```
① 어드민 요청 → 대상 모듈의 핸들러가 자기 트랜잭션으로 커밋
② 응답이 2xx이면 → 감사 로그를 별도 트랜잭션으로 기록
```

### 근거

**B의 정확성보다 C의 누락 없음이 낫다.** 어느 쪽도 원자적이지 않다면, 남는 비교 축은
"얼마나 정확한가"와 "얼마나 빠뜨리는가" 둘이다. 감사 로그에서 더 나쁜 실패는 **없는 것**이다.
"이 변경의 before 값이 로그에 없다"보다 "이 변경이 로그에 아예 없다"가 훨씬 나쁘다.
C는 후자를 구조적으로 막는다 — 기록을 잊으려면 미들웨어를 떼어야 한다.

**A는 조회가 성립하지 않는다.** 감사 로그의 용도는 "무엇이 언제 바뀌었나"를 시간순으로
훑는 것이다. 모듈별로 흩어지면 그 질의가 애플리케이션 조인이 되고, 정렬·페이징이 깨진다.

**미들웨어는 Api 호스트가 아니라 Identity가 제공한다.** 소유자가 기록 방법도 갖는다.
Api는 파이프라인에 꽂기만 한다 — 다른 모듈은 Identity를 참조할 수 없고 Api만 할 수 있다
(docs/modules.md 참조 규칙 표).

## 대가 — 명시적으로 받아들이는 것

1. **감사 로그가 유실될 수 있다.** ①이 커밋된 뒤 ②가 실패하면 변경은 남고 기록은 없다.
   기록 실패는 요청을 실패시키지 않는다 — 감사 때문에 정상 변경을 되돌리는 것이 더 나쁘다.
   대신 `Error` 레벨로 남긴다.
2. **before-after가 값 수준이 아니다.** 요청 본문을 `after`의 근사로 저장한다.
   `before`는 없다. 정확한 diff가 필요해지면 B를 A 위에 얹어야 하며, 그때는 감사가
   각 모듈의 트랜잭션에 들어가야 한다.
3. **읽기 요청은 남기지 않는다.** `GET /api/admin/*`은 기록하지 않는다. 변경 이력이 목적이고,
   조회까지 남기면 신호가 소음에 묻힌다.
4. **실패한 요청은 남기지 않는다.** 4xx/5xx는 바뀐 것이 없다. 인가 실패 추적은 감사 로그가
   아니라 애플리케이션 로그의 일이다.

## 재검토 조건

- 규제 요건으로 정확한 before-after가 요구될 때 → B를 A 위에 얹는다.
- 감사 로그 유실이 실제로 관측될 때 → 아웃박스(ADR 0004)에 얹어 최소 1회 전달로 바꾼다.
  같은 모듈이 아니므로 대상 트랜잭션에 넣을 수는 없지만, 유실은 없앨 수 있다.
- 어드민이 아닌 행위(고객의 취소 등)까지 감사가 필요해질 때 → 경로 접두사 기준을 다시 짠다.
