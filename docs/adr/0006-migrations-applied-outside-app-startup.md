# ADR 0006 — 마이그레이션을 앱 기동 경로 밖에서 적용한다

- 상태: 채택
- 일자: 2026-09-02
- 관련: ADR 0001

## 배경

`docker compose up` 한 번으로 전체가 뜨는 것을 목표로 한다.
그러려면 컨테이너 어딘가는 스키마를 만들어야 한다.

제약은 처음부터 있었다. **앱 기동 경로에서 스키마를 바꾸지 않는다.**
이유는 셋이다.

- 기동 경로에 쓰기가 들어가면 롤백·재기동이 스키마 변경과 얽힌다.
- 여러 인스턴스가 동시에 뜨면 같은 마이그레이션을 동시에 적용하려 든다.
- 무엇보다 운영에서 스키마 변경은 **사람이 보고 승인하는 사건**이지
  배포의 부수 효과가 아니다.

동시에 모듈이 5개라 DataSource도 5개다. 각자 자기 스키마와 마이그레이션 히스토리 테이블을 갖는다.

TypeORM에는 함정이 하나 더 있다. `synchronize: true`는 엔티티 정의와 DB를 맞추려고
**컬럼을 지우는 DDL을 조용히 생성한다.** 개발 편의 기능이며 이 프로젝트의 전제와 정면으로 충돌한다.

## 결정

**마이그레이션은 리포에 커밋된 파일이고, 일회성 `migrator` 컨테이너가 적용한다.**

1. **모든 환경에서 `synchronize: false`, `migrationsRun: false`.**
   앱은 스키마를 바꿀 경로를 갖지 않는다.
2. 마이그레이션 파일은 모듈별 `persistence/migrations/`에 두고 **커밋한다.**
   내용은 `queryRunner.query()`에 담긴 raw SQL이므로, PR 디프에서 DDL이 그대로 읽힌다.
3. `migration:generate`의 출력은 **초안으로만 쓴다.** 부분 유니크 인덱스와 함수 인덱스는
   생성기가 만들지 못하므로 손으로 적고, 생성된 것도 사람이 읽고 커밋한다.
4. compose의 `migrator` 서비스가 모듈 5종의 `migration:run`을 순차 실행하고 종료한다.
   `api`는 `service_completed_successfully` 조건으로 그 뒤에 뜬다.
5. 운영에서는 같은 명령을 배포 파이프라인의 명시적 단계로 실행한다.
   **로컬과 운영이 같은 명령을 쓴다.**

모듈끼리 스키마를 넘는 FK가 없으므로 **모듈 간 실행 순서에 의존하지 않으며**,
각 마이그레이션은 자기 히스토리 테이블을 보고 미적용분만 실행하므로 재실행 안전하다.

## 대안과 기각 사유

### `synchronize: true` (개발 환경만)

기각. "개발에서만"이 지켜진 적이 없다는 것이 첫 번째 이유이고,
개발에서조차 컬럼 삭제 DDL이 예고 없이 실행된다는 것이 두 번째다.
무엇보다 **이 프로젝트가 검증하려는 제약이 스키마에 있다.** 부분 유니크 인덱스가
생성기의 판단에 따라 사라질 수 있다면 동시성 테스트가 무엇을 증명하는지 알 수 없게 된다.

### 앱 부팅 시 `migrationsRun: true`

기각. 배경에 적은 세 가지 이유 그대로다. 절대 규칙이며 이 ADR이 그 규칙의 대안을 제시한다.

### 마이그레이션 SQL을 별도 파일로 뽑아 `psql`로 적용

기각. TypeORM에는 idempotent SQL 스크립트 생성기가 없다.
직접 만들면 히스토리 테이블 관리를 도구와 스크립트가 이중으로 갖게 되고,
**"어느 쪽이 진실인가"가 모호해진다.** 마이그레이션 파일이 이미 SQL을 담고 있어
"DDL을 깃에서 읽는다"는 목적은 그것으로 달성된다.

### init 컨테이너 없이 `psql`을 수동 실행

기각. 한 방 기동이라는 목표를 포기하는 선택이다.
compose의 `service_completed_successfully` 조건이 순서를 보장하므로 자동화 비용이 거의 없다.

## 결과

**얻는 것**
- 스키마 적용 주체가 앱이 아니라 눈에 보이는 일회성 컨테이너다.
- DDL이 PR 디프에 그대로 드러난다. 리뷰어가 인덱스 술어를 읽을 수 있다.
- 운영과 로컬이 같은 명령을 쓴다.
- 앱 이미지는 스키마를 바꿀 수단이 없다.

**비용**
- 생성기 출력을 손으로 고치는 단계가 생긴다. 잊으면 부분 인덱스가 빠진 채 배포된다.
  → 이를 막기 위해 **인덱스의 존재를 통합 테스트가 직접 확인한다**(`pg_indexes` 조회).
  문서로 부탁하지 않고 실패하게 만드는 것이 이 프로젝트의 방식이다.
- 엔티티를 고치고 마이그레이션 추가를 잊어도 앱은 뜬다. 컬럼이 없어 런타임에 깨진다.
  → CI가 마이그레이션 적용 후 스키마와 엔티티 메타데이터를 대조한다.

## 검증

M0 완료 기준에 포함한다. 아직 실행하지 않았으며, 통과 시 이 절에 결과를 적는다.

- `docker compose up` → 스키마 5종 생성, 테이블 확인
- migrator 3회 연속 재실행 → 두 번째부터 적용 0건, 종료 코드 0
- `synchronize`가 `true`인 설정이 코드베이스에 없음을 아키텍처 테스트가 확인

## 재검토 조건

- 인스턴스가 여러 대가 되어 배포 파이프라인이 생길 때
  → migrator를 compose가 아니라 파이프라인의 명시적 단계로 옮긴다.
- 마이그레이션 되돌리기가 실제로 필요해질 때
  → `down()` 구현 정책을 정한다. 현재는 전진만 하며 `down()`은 작성하되 신뢰하지 않는다.
