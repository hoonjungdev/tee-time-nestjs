# ADR 0002 — TeeSlot을 Booking 모듈이 소유

- 상태: 채택
- 일자: 2026-09-02
- 관련: ADR 0001, ADR 0003

## 배경

`TeeSlot`(예약 가능한 티오프 자리)을 어느 모듈이 소유할지 결정해야 한다. 후보는 셋이었다.

1. **Catalog** — 골프장 마스터 데이터의 일부로 본다
2. **독립 Inventory 모듈** — 재고를 독자적 관심사로 본다
3. **Booking** — 예약과 함께 둔다

Catalog는 일찍 기각했다. 슬롯은 정적인 마스터 데이터가 아니라 매일 생성·소비되는 재고이고,
Catalog는 변경 빈도가 낮은 정의성 데이터를 담는 곳이기 때문이다.

남은 것은 **독립 모듈 vs Booking**이었고, 독립 Inventory 모듈은 이커머스에서 흔한 정당한 패턴이다.

## 결정

**`TeeSlot`은 Booking 모듈이 소유한다.**

단, 논리적 독립성은 유지한다. `Booking/Domain/Slots/`와 `Booking/Domain/Bookings/`를
폴더 수준으로 분리하고 참조는 `Bookings → Slots` 단방향만 허용한다.
재검토 조건이 성립하면 `Slots/`를 통째로 들어낼 수 있어야 한다.

추가로, 슬롯은 **점유 상태를 저장하지 않는다.** 점유는 활성 예약의 존재로 파생된다.

## 대안 — 독립 Inventory 모듈을 기각한 이유

### 1. 점유라는 하나의 사실이 두 모듈에 나뉘어 저장된다

분리하면 `inventory.tee_slots.status`와 `booking.bookings.status`가 동시에 존재하는데,
이 둘은 별개의 정보가 아니라 **같은 사실의 두 표현**이다.
서로 다른 모듈이 소유하는 순간 어긋난 상태가 물리적으로 가능해진다.

- 슬롯은 Held인데 예약 레코드가 없음 → 아무도 쓸 수 없는 유령 재고
- 예약은 Held인데 슬롯은 Available → 오버부킹. 실제 사고

### 2. 원자성이 깨지고 사가가 필요해진다

```
① Booking → Inventory.ReserveAsync(slotId)   커밋됨 (별도 트랜잭션)
② Booking: bookings INSERT                    실패 (제약 위반 / 타임아웃 / 프로세스 다운)
   → 슬롯은 점유됐는데 예약이 없다
```

ADR 0001의 "모듈 경계를 넘는 트랜잭션 금지" 원칙상 ①②를 한 트랜잭션으로 묶을 수 없다.
해결하려면 보상 트랜잭션(그 자체도 실패 가능), 사가 상태 저장소, 유령 재고 회수 배치가 필요하다.

**이 복잡도는 전부 도메인 요구사항이 아니라 모듈을 나눈 선택이 만들어낸 것이다.**
같은 모듈이면 하나의 트랜잭션으로 끝난다.

### 3. 재고 소비자가 하나뿐이다

현재 슬롯을 점유하는 주체는 일반 예약 하나뿐이다.
**소비자가 하나인 재고는 그 소비자의 일부다.**

### 반론: "어드민의 슬롯 생성은 예약과 무관하지 않은가?"

무관하지만, 그것은 분리 근거가 아니다. **"누가 쓰느냐"가 아니라 "누가 소유하느냐"가 기준이다.**
슬롯 생성은 `Booking/Features/GenerateSlots/`라는 또 다른 feature일 뿐이다.
사용자가 다르다고 모듈을 나누기 시작하면 결국 "고객 모듈 / 어드민 모듈"로 수렴하며,
그것은 계층을 잘못 자른 것이다.

## 결과

- 홀드 트랜잭션이 하나의 로컬 트랜잭션 안에서 완결된다 → ADR 0003
- 슬롯 row는 쓰기 경로에서 **동시 예약을 직렬화하는 락 대상** 역할을 한다.
  이 역할 때문에 예약에서 물리적으로 분리할 수 없다.
- 점유 상태를 슬롯에 저장하지 않으므로 상태 드리프트가 원천적으로 불가능하다.
- Booking 모듈이 두 애그리거트를 갖게 되어 다소 커진다. 폴더 분리로 완화한다.

## 재검토 조건

아래 중 **하나라도** 성립하면 `Domain/Slots/`를 독립 Inventory 모듈로 승격한다.

1. **재고 소비자가 둘 이상이 될 때** — 일반 예약 외에 대회 블록, 단체 블록, VIP 홀딩처럼
   예약과 무관한 점유 주체가 생기면 재고가 Booking보다 상위 개념이 된다.
2. **채널별 할당량 정책이 생길 때** — 자사앱 40% / 제휴사 40% / 전화 20% 같은 배분이 들어오면
   재고 관리가 독자적인 도메인 로직을 갖는다.
3. **재고를 외부 시스템이 소유할 때** — 골프장 자체 CRM이 재고의 원본이고 우리는 동기화만 하는 구조.
   실제 티타임 플랫폼은 대개 이렇다.

**그 전까지 재고 분리를 제안하지 않는다.**
