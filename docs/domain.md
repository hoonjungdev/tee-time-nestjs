# 도메인

## 개요

골프장의 티오프 시각(티타임)을 재고로 삼아 고객에게 판매하는 예약 플랫폼.
재고 단위는 **슬롯 1개 = 1팀(최대 4인)** 이며, 슬롯은 통째로 점유된다.

도메인의 본질적 어려움은 두 가지다.

1. **동시성** — 예약 오픈 시각에 다수 고객이 같은 슬롯을 동시에 요청한다. 오버부킹은 실제 사고다.
2. **시간** — 사업적 진실은 골프장의 로컬 시각이고, 절대 시각은 파생값이다.

## 애그리거트

Booking 모듈이 두 애그리거트를 소유한다. 참조 방향은 `Booking → TeeSlot` 단방향이며 역방향 참조를 만들지 않는다.

### `TeeSlot`
재고의 **정의**. "이 코스의 이 시각에 티오프 자리가 존재한다"는 사실만 표현한다.

- **상태 컬럼을 갖지 않는다.** 점유 여부는 활성 예약의 존재로 파생된다.
- 쓰기 경로에서의 존재 이유는 **동시 예약을 직렬화하는 락 대상**이다.
- `IsBlocked`는 휴장·정비 등 예약과 무관한 차단 전용이며, 점유와 혼동하지 않는다.

### `Booking`
슬롯에 대한 고객의 점유와 그 생명주기.

## 상태 머신

```
        ┌──────────────────────► Expired      (홀드 TTL 초과)
        │
     Held ──► Confirmed ──► Completed         (티오프 시각 경과)
        │         │
        │         └────────► Cancelled        (고객 / 어드민 취소)
        │
        └──────────────────► Cancelled        (결제 실패 보상, CancelledBy = System)
```

| 전이 | 트리거 | 부수 효과 |
|---|---|---|
| `→ Held` | 고객이 슬롯 선점 | `HoldExpiresAt = now + 10분` |
| `Held → Confirmed` | 결제 승인 성공 | 아웃박스에 `BookingConfirmed` 기록 (동일 트랜잭션) |
| `Held → Expired` | TTL 초과 | 다음 홀드 시도 시 락 안에서 전이 (아래 참조) |
| `Held → Cancelled` | 결제 승인 실패 | 홀드 해제(보상). `CancelledBy = System`, 환불액은 해당 없음 |
| `Confirmed → Cancelled` | 고객/어드민 취소 | 환불액 계산, 아웃박스에 `BookingCancelled` |
| `Confirmed → Completed` | 티오프 시각 경과 | 배치 |

**`Expired`가 별도 상태인 이유:** PostgreSQL의 부분 인덱스 술어는 IMMUTABLE 함수만 허용하므로
`now()`를 쓸 수 없다. 즉 "만료되지 않은 홀드"를 인덱스 조건으로 표현할 수 없다.
따라서 만료는 **읽기 판정이 아니라 쓰기**여야 하며, 홀드 시도 시 슬롯 락 안에서 전이시킨다.
상세는 `docs/schema.md`.

**전이 규칙:** 상태 변경은 도메인 메서드로만 수행한다. `booking.Status = X` 형태의 직접 대입을 허용하지 않는다.

## 도메인 불변식

구현이 반드시 지켜야 하는 것들. 각 항목은 테스트로 검증한다.

1. 하나의 슬롯에 활성 예약(`Held` 또는 `Confirmed`)은 **최대 1건**이다.
2. 만료된 홀드는 슬롯을 점유하지 않는다. 만료 후 동일 슬롯 재예약이 가능해야 한다.
3. 확정된 예약의 금액은 이후 요금표 변경에 영향받지 않는다. (예약 시점 스냅샷)
4. 티오프 시각으로부터 리드타임(기본 2시간) 이내의 슬롯은 예약할 수 없다.
5. 과거 시각의 슬롯은 예약할 수 없다.
6. `IsBlocked = true`인 슬롯은 예약할 수 없다.
7. 예약 인원은 1 이상 `TeeSlot.Capacity` 이하다.
8. 예약 확정과 `BookingConfirmed` 이벤트 기록은 원자적이다. 하나만 성립할 수 없다.
9. 동일한 `(UserId, IdempotencyKey)` 요청은 예약을 1건만 생성한다.
10. 슬롯의 로컬 시각(`TeeDate` + `TeeTime`)이 진실이고, `TeeAt`은 생성 시점에 계산된 파생값이다.

## 요금 정책

MVP 범위: **요일 구분 × 시간대 구분** 2차원.

| 축 | 값 |
|---|---|
| `DayType` | `Weekday` / `Weekend` |
| `TimeBand` | `Early` (~08:59) / `Mid` (09:00~13:59) / `Late` (14:00~) |

- `TimeBand` 판정은 **로컬 시각(`TeeTime`) 기준**이다. 절대 시각으로 판정하지 않는다.
- 규칙은 `(CourseId, DayType, TimeBand)` 조합으로 조회하며, `Priority`가 높은 규칙이 이긴다.
- 매칭되는 규칙이 없으면 예약을 거부한다. (기본값으로 얼버무리지 않는다)
- 계산 로직은 순수 함수로 격리한다. 나중에 회원등급·시즌 요금이 붙으면 그대로 들어낼 수 있어야 한다.

### `TimeBand`의 역할

두 곳에서 쓰인다.

1. **요금 결정 축** — `(CourseId, DayType, TimeBand)`로 `GreenFeeRule`을 조회한다. 주 용도.
2. **검색 필터** — `GET /api/courses?timeBand=`의 시간 조건이자, 사용자가 "09:00~13:59" 대신
   "2부"를 고르게 하는 UI 어휘.

**저장하지 않는 파생값이다.** `tee_slots`에 `time_band` 컬럼을 두지 않으며 `TeeTime`에서 매번 계산한다.
저장하면 경계값 변경 시 기존 슬롯을 전부 재계산해야 하는데, 계산 비용은 무시할 수준이다.

### 알려진 한계 — 공휴일을 반영하지 않는다

`DayType` 판정은 **요일만** 본다. 토·일이면 `Weekend`, 그 외는 `Weekday`다.
용어표의 정의는 "주말·공휴일"이지만 MVP에는 공휴일 캘린더가 없으므로
평일에 걸린 공휴일(예: 어린이날)은 주중 요금으로 계산된다.

의도적 단순화다. 필요해지면 `catalog`에 공휴일 날짜 집합을 두고
판정 함수에 인자로 주입한다 — 판정을 순수 함수로 격리해 둔 이유 중 하나다.

### 알려진 한계 — 경계값이 전역 상수다

`Early`/`Mid`/`Late`의 경계(08:59 / 13:59)를 **모든 코스에 동일하게 적용**한다.
실제 골프장은 1부/2부 경계가 사업장마다 다르고, 계절에 따라 일출 시각 때문에 옮기기도 한다.

MVP에서는 의도적으로 단순화했다. 확장이 필요해지면:

- 경계 컬럼을 `catalog.courses` 또는 `catalog.operating_rules`에 추가한다
- 판정 함수의 인자만 늘어나면 되도록, 로직은 **Catalog 안의 순수 함수로 격리**해 둔다
  (이것이 격리를 요구하는 실질적 이유다)

검색 성능 관련 한계는 `docs/schema.md`의 `ix_slots_search` 항목 참조.

## 취소·환불 정책

티오프 시각까지 남은 시간 기준. 순수 함수 + 단위 테스트로 검증한다.

| 취소 시점 | 환불율 |
|---|---|
| 티오프 7일 전 초과 | 100% |
| 3일 초과 ~ 7일 이하 | 80% |
| 1일 초과 ~ 3일 이하 | 50% |
| 1일 이하 | 0% |

- 어드민의 강제 취소는 정책과 무관하게 100% 환불하며, `CancelledBy = Admin`과 사유를 반드시 기록한다.
- 남은 시간 계산은 절대 시각(`TeeAt`) 기준이다.
